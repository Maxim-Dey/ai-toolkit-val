# Design

## Context

Мотивация — в `proposal.md`. Источники требований: `intent_val-loss.md` и `config/qwen_image_21_kibm.yaml`. Указания про удалённые проверки в интенте описывают будущую приёмку; на этапе предложения команды на RunPod не выполняются.

Наблюдения по текущему коду:

| Область | Текущее поведение и точка изменения |
| --- | --- |
| Конфиг | `BaseSDTrainProcess.__init__` читает `datasets`; `DatasetConfig` — `folder_path` / `dataset_path`. `train_datasets`, `train_path`, `val_datasets`, `val_path` согласованного файла ещё не обслуживаются. `training_seed` и `sample_start_step` уже поддержаны. |
| Валидация | `setup_validation` кэширует только цель, текст и один шум; VAE seed общий для последовательного обхода, noise seed равен `42+i`. `validate` объединяет уровни в батч, вычисляет самостоятельный MSE, пишет `additional_logs['val/loss']`. Вызов идёт после обучающего прохода, восстановления режимов через `finally` нет. |
| Loss | `SDTrainer.calculate_loss` уже содержит цель модели, маски, веса timestep и SNR. `train_single_accumulation` отдельно готовит маску и условия и выполняет backward. Расчёт loss имеет побочные эффекты: дополнительные логи, потребление `adapter.additional_loss`, вызов обучаемого SNR. |
| Данные | `dataloader_mixins.py` содержит случайный выбор контролей, генерацию `controls`, случайное размытие маски. `DataLoaderBatchDTO` передаёт маски и списки контролей, но допускает заполнение некоторых отсутствующих входов. Для val это нужно заменить строгой проверкой. |
| Модели | Qwen-Image-2.1 передаёт контроли одновременно в текстовый энкодер и VAE, а `get_noise_prediction` заново вызывает `encode_condition_images`. MOSS имеет режим `model_kwargs.edit`, мультимодальный текст и `_batch_ref_latents`. Qwen-Image имеет отдельную обёртку. Нельзя считать все три семейства одинаковыми по входам. |
| Шум | `CustomFlowMatchEulerDiscreteScheduler.add_noise` уже использует `timestep/1000`. `get_weights_for_timesteps` ищет точное совпадение в расписании; `apply_snr_weight` приводит индекс к int. Это несовместимо с произвольной дробной точкой val. |
| Шаги | Оптимизатор обновляется в `SDTrainer.hook_train_loop`, а внешний `step_num` — индекс цикла. Есть два способа накопления и обработка OOM. Конечное сохранение вызывается отдельно без номера. |
| Вывод | `BaseTrainProcess` создаёт TensorBoard только при `log_dir`, с каталогом по времени. `save` пишет плоские LoRA-файлы и один общий `optimizer.pt`; поиск последнего сохранения использует время создания. |
| Проверки | Есть `testing/` с unittest и модельными скриптами, данные `datasets/kib_medium/train` и `val`, CLI `run.py`; TensorBoard есть в `requirements_base.txt`. Наличие каталогов не доказывает пригодность всех данных или доступность удалённого GPU. |

## Goals / Non-Goals

**Goals:** использовать существующий путь подачи входов и расчёта loss, выделив минимальную границу между вычислением и обновлением состояния; сделать валидируемые данные независимыми от обучающего загрузчика; сохранять согласованный YAML как рабочий публичный интерфейс.

**Non-Goals:** создавать универсальный движок оценки, переносить весь trainer на новую архитектуру, добавлять новые режимы контроля моделям, менять обучающие аугментации или заменять `adamw8bit`. Квантизация состояния оптимизатора не является квантизацией модели: согласованный оптимизатор остаётся, `quantize` и `quantize_te` остаются false.

## Decisions

### 1. Нормализация конфига на границе

Добавить конфигурацию val в `toolkit/config_modules.py`, нормализовать новые пути в существующий `DatasetConfig` до обработки списков разрешений. `train_datasets` заменяет только внешний способ задания train. Конфликт с `datasets`, конфликт альтернативных полей пути и совместное задание старого `train.validation_config` и `val_datasets` — ошибки, а не приоритет «последний победил».

Без новых полей сохраняется старый путь выполнения. Новый счётчик и раскладка LoRA включаются при `train_datasets` или `val_datasets`; новый val — только при непустом `val_datasets`. Явный пустой список — ошибка. Проверка поддерживаемой модели учитывает arch и обёртку, в том числе локальные веса, а не только строку Hub ID.

Решение для нескольких val-датасетов: один объединённый проход, одинаковые interval/seed/N1/N2, группировка одинаковых целей по хешу содержимого. Это позволяет сохранить ровно три общих графика. Несовпадение параметров — понятная ошибка; независимые расписания и новые теги сейчас не нужны. Согласованный конфиг содержит один набор и этому правилу соответствует.

Val не наследует пути, dropout и аугментации train. Общие алгоритмы подготовки используются с отдельным детерминированным профилем: `.txt`, пустой default caption, нет случайного crop/flip/размытия/dropout/shuffle, один проход без repeats. Явно заданные случайные настройки val отклоняются; пропущенные получают безопасные детерминированные значения. Маски и их настройки задаются в val явно. Разрешения обрабатываются детерминированно; несколько разрешений образуют фиксированные варианты одной цели, а не увеличивают её вес. Альтернатива с передачей val в обычный shuffle-dataloader отвергнута из-за случайностей и повторов.

### 2. Фиксированная запись входов и манифест

Небольшой модуль `toolkit/validation.py` хранит описание прохода и подготовленные записи; общий trainer управляет жизненным циклом. Не создавать отдельную систему датасетов: использовать текущие правила соответствия файлов, bucket/resize, DTO и подготовку контролей, добавив детерминированный режим и строгую проверку обязательных входов.

Запись содержит hash цели, текст, маску, упорядоченный список совместных контролей, настройки подготовки и фиксированные tensors/embeddings. Отдельные записи с тем же hash цели — альтернативы; точные дубликаты записей устраняются. Разные формы latent получают свои фиксированные tensors, но seed всё равно определяется только целью и индексами проверки.

Версионированный манифест включает SHA-256 исходных файлов, фактический текст после детерминированной обработки, роли и порядок контролей, соответствия, bucket/resize, mask_min_value/invert, настройки генератора автоматических контролей, идентичность модели/энкодеров и версии подготовки. Перечень записей канонически сортируется; порядок обхода файлов и абсолютный префикс каталога не определяют идентичность. Порядок контролей внутри записи значим. Проверяются также пересечения хешей целей train и val.

Перед каждым проходом перечитать состав и хеши входов; сравнить с исходным манифестом, при изменении остановить запуск без новых метрик. При resume проверять до обновлений и до перезаписи сведений прежнего запуска. Созданный автоматически контроль тоже входит в манифест. Хеш манифеста, его версия и описания записей сохраняются в состоянии чекпоинта; tensors можно воспроизводимо восстановить, их отдельная обязательная копия в выходной структуре не нужна.

### 3. Изолированная подготовка, включая контроли

Подготовить val, пока доступны VAE и текстовый энкодер, до их выгрузки. Для каждой записи и роли входа использовать отдельный seed подготовки из SHA-256 с меткой роли, hash содержимого и настройками. Не использовать общий RNG-поток на весь список. Сохранить и восстановить Python, NumPy, CPU/CUDA PyTorch RNG всех задействованных устройств через `try/finally`; генераторы шума — отдельные CPU generators. Область изоляции охватывает и автоматическую генерацию контролей.

Не менять алгоритм VAE обучения: фиксировать его стохастический результат для val с локальным seed. Нормализованные маски не размывать случайно. Использовать обычные правила пространственных преобразований выбранного режима: reference-изображения не обязательно имеют crop цели, а spatial control и маска сохраняют нужное соответствие.

В DTO добавить необязательные подготовленные condition latents и сопутствующие формы/метаданные. Обёртки Qwen-Image-2.1, Qwen-Image-Edit-2511 (`qwen_image_edit_plus`) и MOSS читают их в val вместо повторного VAE; обычный train продолжает существующий путь. Текст кодируется с теми же контролями и в том же порядке, что latent conditioning. Для Edit-2511 выделить общую с train подготовку одного контроля: resize с учётом `match_target_res`, VAE и упаковка токенов; сохранить чистые packed latents и формы на CPU. Каждый контроль получает отдельный seed подготовки. Отсутствие обязательных контролей Edit-2511 в train или val отклонять при preflight; маска loss не заменяет контроль. Для Qwen-Image/2512 проверить существующие адаптерные пути; неподдерживаемый native control отклонять, доступные сочетания адаптера сохранять. Для MOSS контроли обслуживаются в существующем `edit`-режиме; это не обещание поддержки контролей при `edit=false`.

Альтернатива «переустанавливать один seed перед каждым предсказанием» отвергнута: она оставляет дорогое повторное кодирование и зависимость RNG от внутреннего порядка операций.

### 4. Сетка и сериализация seed

Генерировать уровни в float64 по формуле спецификации, передавать timestep как float32 без целочисленного преобразования; допустимо обычное округление представления float, но не привязка к узлам расписания. Использовать существующую формулу смешивания без вызова shift. Конвертация в собственный формат модели остаётся за обёртками.

Зафиксировать `stable_hash` для noise версии 1: компактный UTF-8 JSON-массив `[val_seed_noise, image_sha256_hex_lowercase, i, j]` без пробелов, SHA-256, первые 8 байт big-endian с маской `0x7fffffffffffffff`. Генерировать стандартный нормальный шум CPU float32, затем переносить в dtype/device latent. Seed подготовки имеет отдельную метку назначения и не переиспользует noise-поток. Проверки исполняются по стабильному порядку цель → набор → i → j, батч всегда 1.

### 5. Общий loss без обновлений

Выделить из `train_single_accumulation` общий расчёт предсказания/цели/loss на уже подготовленном DTO. Переиспользовать `calculate_loss` и подготовку mask multiplier, сохранив маску, её нормализацию, модельную цель и scale, network_weight и настроенные множители. Backward, optimizer.step, scheduler.step и обновления адаптеров остаются только в обучающем пути.

Разделить чистое вычисление и побочные эффекты внутри loss: локальные val-логи не попадают в `additional_logs` обучения; временный `adapter.additional_loss` не потребляет обучающее значение; обучаемый SNR имеет режим чтения коэффициентов без внутреннего backward/step и накопителей. Если конкретная loss/adapter-комбинация не предоставляет корректный режим чтения, preflight сообщает её как неподдерживаемую. Нельзя отвергать маску или поддерживаемый контроль просто ради упрощения val.

Для включённых табличных весов использовать линейную интерполяцию по числовым координатам исходного расписания. Сортировать пары `(timestep, weight)` вместе; на узле сохранять прежнее значение. Не подменять timestep ближайшим и не менять training scheduler ради val. Это распространяется и на SNR-таблицы, где старое приведение к int недопустимо. Обучаемые коэффициенты применяются после получения корректной величины для заданного t. Неоднозначные узлы, отсутствие определённой таблицы/формулы и выход за диапазон отклоняются при preflight. Согласованный `timestep_type: shift` сам по себе не включает дополнительное loss-взвешивание.

Preflight до первого обновления проверяет тип loss, комбинацию опций и возможность вычислить все уровни. Первый полный val на шаге 0 или resume выявляет ошибки модельных входов до обновления весов. Альтернатива с отдельным MSE отвергнута: она нарушает сравнимость с настроенным обучением.

### 6. Граница прохода и завершённый шаг

В новом режиме хранить `completed_optimizer_steps` отдельно от индекса микробатча. Увеличивать только после фактически выполненного optimizer.step (учитывая пропуск accelerated optimizer); scheduler обновлений и периодические действия привязать к этому событию. Обе существующие формы accumulation учитываются. OOM не увеличивает шаг; частично накопленные градиенты очищаются по существующему пути ошибки, без ложного сохранения/валидации. `train.steps` в новом режиме — целевое число завершённых обновлений.

После загрузки весов/оптимизатора и подготовки val выполнить стартовый проход до первого получения обучающего батча и до первого семплирования. После завершённого обновления — периодический val; перед завершением — финальный, если этот шаг ещё не проверен в текущем процессе. Resume всегда получает новый стартовый проход, даже если предыдущий процесс писал этот шаг.

Контекст прохода сохраняет training-флаги каждого участвующего модуля, LoRA activity/multiplier, временные adapter buffers, RNG, размещение выгружаемых модулей и изменяемое состояние scheduler. Включает eval и no-grad, активирует обученную LoRA с нужным множителем, восстанавливает всё в `finally`. Не вызывать train hook или zero_grad из val. Проверки снимков параметров/градиентов/optimizer state выполняются в тестах, без дорогостоящего копирования всех весов в рабочем проходе.

Для обычного DDP все процессы ждут границ прохода; главный процесс вычисляет val на доступной нешардированной модели и публикует результат/ошибку остальным, без training collectives. Неподдерживаемое шардированное исполнение нового val отклонять до обучения, чтобы не зависнуть. Согласованный запуск — один `cuda:0`.

Агрегировать конечные скаляры в стабильном порядке и float64: проверки → варианты → уникальные цели. Проверять ожидаемое число результатов и конечность каждого loss до публикации.

### 7. TensorBoard

В `BaseTrainProcess` учитывать включение val до создания writer. По умолчанию использовать `<save_root>/tensorboard/`; при заданном `log_dir` использовать его как явный каталог этого запуска. Resume открывает тот же каталог; записать стартовую оценку восстановленных весов на сохранённом шаге. При откате к старому чекпоинту использовать механизм очистки последующих событий TensorBoard, сохраняя предшествующую историю.

Все три val-скаляра записывать напрямую через writer только после полной агрегации и вызывать flush. Train-loss пишет тот же writer с completed step, соблюдая свой `log_every`. Ошибка вычисления не публикует ни одного скаляра. При ошибке дисковой записи сообщить сбой; атомарность трёх событий при физическом отказе диска не обещается. Дополнительный logging framework не требуется.

### 8. Чекпоинт как единый каталог

Для нового LoRA-режима централизовать путь шага в `BaseSDTrainProcess`; формат — минимум шесть цифр. Сохранять `model.safetensors` FP32 один раз, `optimizer.bin` как версионированный контейнер состояния выбранного оптимизатора, LR scheduler, completed step, RNG, нужных обучаемых loss-состояний и val-манифеста. Metadata LoRA тоже содержит шаг и идентификатор состояния для перекрёстной проверки.

Писать во временный соседний каталог, публиковать после успешного сохранения обязательных файлов. Если каталог уже содержит стартовые/периодические samples, сохранить их при завершении чекпоинта; использовать признак завершённого состояния и проверку файлов, а не наличие каталога. Неполные каталоги не участвуют в автоматическом resume и ротации. Ошибка оптимизатора больше не маскируется успешным сообщением о полном чекпоинте.

Семплирование на шаге S пишет в `<name>-stepSSSSSS/samples/`. До первого сохранения допустим каталог только с samples (включая шаг 0). Если включено EMA, выбор весов для сохранения и семплирования должен совпадать; исходные обучающие веса после операций восстанавливаются. Последний шаг сохраняется по тому же правилу; повторный save на том же шаге не создаёт копий. Ротация по номеру завершённого шага удаляет каталог целиком после успешного нового сохранения.

Старые flat-файлы и `optimizer.pt` читаются старым режимом. Новый режим допускает загрузку старой LoRA как начальных весов нового запуска. Точный resume разрешён только при доказуемой согласованности состояния и val-манифеста; нельзя восстанавливать старый optimizer неизвестного шага как будто он соответствует выбранной LoRA.

### 9. Проверки и GPU-приёмка

Локальные unittest с небольшими tensors и подставной моделью проверяют сценарии спецификаций: seed и сетку (включая N1=8), интерполяцию, иерархическое среднее, маски, конфиг, график шагов, восстановление при исключении, отсутствие побочных эффектов и layout/resume. Чтение реальных TensorBoard events проверяет теги, flush и шаги. Регрессия общего loss сравнивает прежний обучающий расчёт на фиксированных входах с новым; варианты без val проверяют совместимость.

GPU-приёмка после реализации использует предоставленный RunPod и репозиторный датасет. Последовательно: Qwen-Image → Qwen-Image-2512 → Qwen-Image-Edit-2511 → MOSS-Image-SFT → MOSS-Image-Base → Qwen-Image-2.1-Turbo → Qwen-Image-2.1. Последняя модель остаётся подготовленной для CLI. Загрузку недостающих весов выполняет trainer по исходному репозиторию модели; никаких квантованных замен. Проверить фактические dtype и полноту весов/энкодеров, сохранить ревизии в отчёте. Для итогового Qwen использовать пути согласованного конфига; если локальные файлы отсутствуют, реализовать их получение штатным загрузчиком до запуска обучения, а не молча менять конфиг на другую модель.

На каждой модели короткий тестовый конфиг с 2–3 обновлениями, накоплением, периодическим и финальным val, save и resume. Отдельно проверять без входов, маску, один/несколько готовых контролей, автоматический контроль и маску с контролями во всех поддерживаемых обёрткой/адаптером режимах; неподдерживаемые клетки должны завершаться ожидаемой ошибкой preflight. Зафиксировать таблицу фактической поддержки, а не считать пропуск успешной проверкой.

Основной конфиг не сокращать: маленькие steps, интервалы и батч задавать в отдельных тестовых копиях. Сравнить повторный val, перестановку входов, resume и следующий обучающий шаг с val/без val в том же окружении. Для битового сравнения использовать детерминированные kernels; если конкретное GPU-ядро недетерминировано, отдельно фиксировать точное совпадение входов/RNG и измеренную численную погрешность, не выдавая её за побитовую идентичность.

После каждой модели удалить только скачанные для этого теста ненужные веса, сохраняя общие зависимости итоговой Qwen-Image-2.1. Удалить временные тестовые конфиги/выходы, сохранить отчёт и нужные финальные файлы. Финальная проверка — работоспособность CLI `python run.py config/qwen_image_21_kibm.yaml` и доступность всех путей; не запускать 2500 шагов ради проверки.

### 10. Дополнение после GPU-приёмки: остановка и warmup

По запросу пользователя основной YAML дополняется `train.lr_scheduler: constant_with_warmup` и `train.lr_scheduler_params.num_warmup_steps: 100`. Это уже реализовано в `toolkit/scheduler.py`; новый алгоритм или глобальный default не требуются. После S завершённых обновлений LR равен `0.0001 × min(S/100, 1)`. На старте LR нулевой; после сотого обновления — полный. Накопление, пропуск обновления и val не продвигают расписание. Resume с теми же параметрами восстанавливает scheduler и optimizer, не начинает warmup заново.

Обычный Python-обработчик SIGINT может ожидать возврата из нативного вычисления. Поэтому POSIX CLI `run.py` до импорта PyTorch запускает обучение дочерним процессом в отдельной группе, а лёгкий родитель принимает Ctrl+C/SIGINT и SIGTERM. Он передаёт сигнал группе обучения, даёт 5 секунд на штатное завершение, затем SIGTERM и ещё 5 секунд; оставшиеся процессы завершаются SIGKILL. Повторный сигнал сокращает ожидание. Группа изолирована от терминала, TensorBoard и других запусков. Внутренний запуск не создаёт ещё одного родителя. Успех и ошибки сохраняют exit code, прерывание возвращает 130 для SIGINT; `--recover` не продолжает очередь после Ctrl+C. Windows и импорт `run.py` сохраняют прямой путь исполнения.

Прерывание не заявляет сохранение текущего незавершённого обновления и не запускает новый save/val/sample; для resume пригодны только ранее опубликованные полные чекпоинты. Проверки дополнения: реальные CPU-процессы и PTY на Linux, зависший/игнорирующий сигналы потомок, очистка дочерних процессов, сохранность постороннего процесса, CPU-проверки warmup/accumulation/resume и прежний набор регрессий. GPU-проверки и полное обучение для этого дополнения не запускать. Исторические GPU-отчёты остаются свидетельством прежней приёмки, а не проверки нового дополнения.

## Risks / Trade-offs

- Стоимость `20 × число наборов` предсказаний на проход в согласованном конфиге → батч 1 и CPU-кэш; не урезать набор и не пропускать проверки ради ускорения.
- Скрытые случайности и mutable buffers в обёртках/адаптерах → общий контекст изоляции, подготовленные контроли, сравнение состояния при успехе и исключении.
- Перенос времени вызова влияет на labels, save и sample → один completed-step источник для всех действий нового режима и проверки accumulation/OOM/resume.
- Различия библиотек или GPU при resume → версионировать подготовку, фиксировать окружение; несовместимую подготовку выявлять до обновлений. Межплатформенная побитовая идентичность не заявляется.
- Не хватает GPU-памяти для неквантованных весов → использовать доступное штатное размещение/offload в тестовых конфигах или зафиксировать блокировку конкретного GPU-теста; не подменять модель квантованной.
- Новый формат не читается старой версией trainer → сохранять старые файлы, не мигрировать их автоматически; для отката использовать прежний конфиг и прежние чекпоинты.

## Migration Plan

1. Ввести и проверить новый интерфейс, оставив старый путь доступным.
2. Провести CPU-регрессии и последовательную GPU-приёмку до использования нового формата в длительном запуске.
3. Запускать согласованный конфиг как новый запуск; для resume использовать только завершённый новый чекпоинт с совпадающим манифестом.
4. При откате вернуть прежнюю версию и старые конфиги/чекпоинты. Новые данные и журналы не удалять и не преобразовывать автоматически.
